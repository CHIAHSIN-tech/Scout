### C. Prompt（`_build_suggestion_prompt`）

- 角色設定：「你是一位專業的旅遊規劃師」
- 帶入六個答案，未提供者填「未提供」（`extra` 填「無」）
- 要求 JSON 陣列，每元素欄位：`day`、`name`、`category`、`start_time`、`duration_minutes`、`location`、`notes`
- **五條規則**（原文照抄，全部 **在範圍內**）：
  1. 根據天數安排每天的行程，早上約 09:00 開始，合理分配時間
  2. 景點大約 90-120 分鐘，餐廳 60-90 分鐘，購物 60-90 分鐘
  3. 每天安排 4-6 個項目，包含早餐、午餐、晚餐和景點
  4. 行程之間預留合理的移動時間
  5. 只回傳 JSON 陣列，不要任何說明文字或 markdown
- 生成參數：`temperature=0.7`、`max_output_tokens=2048` → **在範圍內**（web 版由 Function 設定）

## 參照系統本身的缺陷（不移植，§7 規則 6）

1. **`category` 沒有白名單驗證。** AI 回傳 `"美食"` 之類的值會原樣寫進資料庫，
   前端 `CATEGORY_LABEL` 查不到就掉回「其他」，但資料庫裡留著髒值。
   → web 版**必須**驗證，這不是 parity，是修掉。
2. **`day` 沒有對照旅程實際天數。** AI 回 `day: 7` 而旅程只有 4 天，照樣寫入，
   之後在行程表／時間軸都看不到（那些檢視依 `totalDays` 迴圈）。
   → web 版必須夾到 `1..totalDays`（`web/checklist.js` 的 `aiRowToFields` 已有此邏輯，可重用）。
3. **`confirm_required` / `is_confirmed` 完全沒設。** Streamlit 時代還沒有這兩軸（ADR-008 之後才有）。
   → web 版須明確寫 `false`，不能讓欄位是 NULL。
4. **勾選狀態用 `set` 存在 session_state，與 checkbox key 雙軌**，Streamlit 重跑時容易不同步。
   → web 版不會有這個結構問題，不移植。

## 我們的情況需要、而參照系統沒有的

| 需求 | 為什麼參照系統沒有 |
|---|---|
| **金鑰不得進前端** | Streamlit 是伺服器端執行，金鑰天生在後端。web 版是靜態站，必須走 Netlify Function（ADR-011，`ai-parse.js` 已是同樣模式，可沿用） |
| **手機可用** | Streamlit 版是桌面導向。本專案第一原則是手機優先 |
| **與「候選」語意相容** | 候選（`day_number IS NULL`）是 ADR-008 之後才有的概念 |
| **不得引入 build step** | ADR-010 |

## 無法觀察的部分（誠實列出）

1. **執行中的畫面**：Streamlit 已退役，跑不起來。上述互動行為全部由原始碼推得，
   **沒有一項是實際操作觀察到的**。間距、實際換行、spinner 的視覺表現無從得知。
   → 影響：視覺細節不做 parity，只做行為 parity。
2. **實際使用頻率與痛點**：無任何使用紀錄或回饋。
   不知道六題是否太長、multiselect 是否真的被用、生成品質是否夠好。
   → 影響：六題全數移植（不自作主張刪題），但 spec 記下「題數可能過長」為待觀察項。
3. **`ai.py` 的 503 重試在實務上有沒有被觸發**：無日誌。
   → 因此重試列為**延後**：現行 `ai-parse.js` 沒有重試也運作正常（AI 匯入行程實測可用），
   等真的遇到再加，不預先做。
