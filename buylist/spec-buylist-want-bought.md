## 1. Problem Statement

**背景**  
BuyList 原本只有「想買清單」，用來記錄想買的東西。CHIA 發現另一個需求：買過的東西容易忘記好不好用、在哪買、值不值得回購，原本考慮做獨立的「辣醬庫」，後來決定改為**併入 BuyList**，成為同一個 app 的「已買」視圖。

**現狀**  
- BuyList 只追蹤「還沒買」的東西，買了之後項目就被刪除或遺忘
- 沒有地方記錄「這個東西我買過、好不好用、要不要再買」

**目標**  
在 BuyList 裡新增「已買」分頁，讓已購買項目可以標星號收藏，並保留購買日期和商品連結，方便未來回購判斷。

## 6. Acceptance Criteria

### 分頁切換
- [ ] **AC-1**：點「想買」/「已買」pill → 立即切換視圖，無轉場動畫
- [ ] **AC-2**：啟用中的分頁背景為 sage-800，文字為 sage-50；未啟用為透明背景、linen-700 文字

### 想買 — 新增
- [ ] **AC-3**：輸入框輸入文字 + 點「+ 加入想買清單」→ 新項目加入清單最上方，status 為 `want`，url 空、starred 為 false、date 為 null
- [ ] **AC-4**：輸入框按 Enter 鍵 → 效果同點擊按鈕
- [ ] **AC-5**：輸入框空白或只有空格 → 不新增（no-op）
- [ ] **AC-6**：提交後輸入框清空

### 想買 — 標記已買
- [ ] **AC-7**：點擊卡片任意處（刪除鈕除外）→ 該項目 status 變為 `bought`，date 設為今天（格式 `YYYY/MM/DD`），並從想買清單消失、出現在已買清單最上方
- [ ] **AC-8**：點刪除鈕不會觸發標記已買（event 需 stopPropagation）

### 想買 — 空狀態 / 刪除
- [ ] **AC-9**：想買清單為空 → 顯示置中斜體文字「想買清單是空的」
- [ ] **AC-10**：點刪除鈕 → 項目從清單移除

### 已買 — 星號與篩選
- [ ] **AC-11**：點星星圖示 → 該項目 starred 狀態切換，圖示填色在 `#C4915A`（已收藏）與空心 `#A8A298`（未收藏）間切換
- [ ] **AC-12**：點「全部」→ 顯示所有已買項目；點「只看星號」→ 只顯示 starred 為 true 的項目
- [ ] **AC-13**：篩選按鈕啟用態：邊框與文字變 sage-800，背景 sage-50，字重 600

### 已買 — 移回想買 / 刪除
- [ ] **AC-14**：點復原圖示 → 該項目 status 變回 `want`，date 清空，從已買清單消失、出現在想買清單最上方
- [ ] **AC-15**：已買清單為空（或篩選後無結果）→ 顯示「還沒有已買記錄」
- [ ] **AC-16**：點刪除鈕 → 項目從清單移除

### URL 欄位（想買 / 已買皆適用）
- [ ] **AC-17**：URL 輸入框變更內容 → 即時儲存（無需額外儲存按鈕）
- [ ] **AC-18**：URL 非空時，卡片顯示「開啟」連結，點擊在新分頁開啟該網址（`target="_blank" rel="noopener noreferrer"`）
- [ ] **AC-19**：URL 為空時，不顯示「開啟」連結

### 排序
- [ ] **AC-20**：兩個清單皆「最新變更在前」——新增、標記已買、移回想買後，項目移動到該清單最上方

### 多人同步
- [ ] **AC-21**：使用者 A 新增/編輯/刪除項目後，使用者 B 的畫面在數秒內自動更新（Firebase Realtime 監聽）

## 7. Build Order

**第 1 loop：資料層 + 想買清單基本 CRUD**
1. 擴充 Firebase items schema：加入 `status`、`starred`、`date`、`url` 欄位
2. 建立 `itemService.js`：`addItem`、`deleteItem`、`updateItem`
3. 建立想買清單畫面：新增表單 + 卡片列表（僅顯示 status='want' 項目）
4. 實作新增、刪除
5. **Tracer bullet 停止點**：能新增一個想買項目，並在清單看到

**第 2 loop：標記已買 + 已買清單**
1. 想買卡片點擊 → 呼叫 `markBought`
2. 建立已買清單畫面（顯示 status='bought' 項目）
3. 實作移回想買
4. 測試：想買 → 已買 → 想買 的完整循環

**第 3 loop：星號 + 篩選**
1. 星號切換功能
2. 篩選「全部/只看星號」
3. 測試：星號狀態正確反映在篩選結果

**第 4 loop：URL 欄位**
1. URL 輸入框（想買 + 已買卡片皆加上）
2. 即時儲存邏輯
3. 「開啟」連結顯示邏輯

**第 5 loop：視覺還原 + 多人同步驗證**
1. 套用 Design Tokens（顏色、字體、間距、圓角）
2. 確認 Firebase Realtime 監聽正常運作（雙分頁測試）
3. 手機寬度視覺 QA（375-420px 無橫向捲動）

## 8. End-to-End Verification

```
1. 開啟 BuyList → 預設在「想買」分頁
2. 輸入「手沖濾杯」→ 點「+ 加入想買清單」
   驗證：清單最上方出現「手沖濾杯」卡片
3. 點擊卡片主體（非刪除鈕）
   驗證：項目消失，切到「已買」分頁能看到「手沖濾杯」+ 今天日期
4. 點星星圖示
   驗證：星星變為實心橘色
5. 點「只看星號」篩選
   驗證：「手沖濾杯」仍顯示（因為已加星號）
6. 貼上網址到 URL 欄位
   驗證：出現「開啟」連結，點擊開新分頁
7. 點復原圖示（移回想買）
   驗證：項目回到「想買」分頁，日期清空，已買清單看不到它
8. 開兩個瀏覽器分頁，一邊新增項目
   驗證：另一邊數秒內自動顯示新項目
```

## 10. Open Questions / Risks

### 已決定
- ✅ 併入 BuyList，非獨立 app
- ✅ 星號收藏取代評分制度
- ✅ 視覺規格已定案，直接依 Design Tokens 實作
- ✅ 想買 ↔ 已買 為同一份資料的狀態轉換（非兩個獨立清單）
- ✅ **圖示庫**：採用 Icon 庫（方案 B，如 Tabler），不手刻 inline SVG。理由：長期維護成本較低，符合專案持續迭代的性質；視覺與設計稿會有些微差異（粗細、弧度），但可接受
- ✅ **Firebase schema 遷移**：不寫 migration script。理由：既有資料量小，改在 `itemService.js` 讀取資料時做預設值防呆（例如 `item.status ?? 'want'`），風險低、上線快；若未來資料量變大，再評估補寫腳本

### 待決定
（無，本輪待決定問題已全數定案）

### 已知風險
- 🚩 設計稿為「無持久化」的純前端原型，正式串接 Firebase 時，需確認 Realtime 監聽與樂觀更新（optimistic update）的時機，避免畫面閃爍
- 🚩 URL 欄位為自由輸入文字（非強制驗證格式），若貼上非網址文字，「開啟」連結行為未定義——建議實作時做基本 URL 格式檢查
