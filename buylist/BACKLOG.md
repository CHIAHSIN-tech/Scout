## 建議：接下來的順序（2026-08-08）

1. **行程 Tab 補回編輯/刪除**（`specs/spec-itinerary-restore-edit-delete.md`）——唯一「以前能做、現在不能做」的地方，優先於任何新功能。
2. **視覺統一 ＋ 日曆／地圖匯出**（`specs/TASK-ui-unify-and-calendar-maps-export.md`）——兩件事合成一份規格；視覺統一愈晚做，錯開的 token 累積愈多。
3. **決定 AI 生成行程要不要補**——Streamlit 退役後真空，需先決定做不做。
4. 購物若要再加，只有三項划算：**關鍵字搜尋**、**依分類折疊分組**、**「誰負責採買」標記**。其餘不是貴就是撞決策。

> **順序理由**：1 是補倒退（現在做不到的事），2 是新增能力，所以 1 先。
> 但 2 的「視覺統一」部分有時間成本——每多改一次樣式，兩邊 token 就多歪一點，所以不宜排太後面。

### 決策紀錄（2026-08-17，Stanley 拍板）

- **主動提醒一律不做**（場合/紀念日提醒、補貨提醒、待買擱太久的主動提醒）。
  理由：靜態站沒有推播層，要做只能靠 PWA（已定案不做）或 email，
  等於為三個小功能引進一整層新基礎建設。**「想買 N 天」這種被動顯示保留**，
  差別在於「打開就看得到」vs「主動跳出來吵你」——只有後者不做。
- **同商品多賣場比價**：要做。需新表，待寫 spec。
  注意這**不算追價**（追價＝追時間序列的降價，仍維持 Won't）；
  多賣場是同一時間點比不同通路，性質不同。
- **AI 生成行程**：要做，**且 web 端要做**。MCP 已經能讓 Claude 直接寫入行程，
  但那條路手機用不到，而本專案第一原則是手機優先——所以兩條並存，不是二選一。
- **AI 相關需求的總方針**：MCP 當桌面的強力路徑，web 端既有的 AI 功能維持不動。
  不把 web 的 AI 搬去 MCP（那會是手機上的功能倒退）。

### 「上手機」待拆解（尚未 spec）
「上手機」不是一個功能，是方向；至少拆成三條，且分屬不同人：
1. **部署/可達性（Stanley，部署範疇）**：手機要能連到 app。現有 app 是單檔靜態 HTML+Supabase，選項如 Cloudflare Tunnel 或靜態託管。⚠️**安全**：從「只在 localhost」變成「公開網址」，等於把 Supabase anon key＋全開 RLS 攤在網址上（誰有網址誰能讀寫）。原本「網址即存取」的風險模型要重新確認能否接受。
2. **手機介面優化（Chia，UI 範疇）**：現行 UI 偏桌面，要做 responsive／手機優先（呼應 Scout 主 app 的「手機優先」原則）。
3. **PWA 離線（之後）**：先能「線上在手機用」，再談離線快取。離線又牽涉「兩人離線各改怎麼合」，是更大的題。
